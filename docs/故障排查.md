# 故障排查

## 1. `torch.cuda.is_available() = False`

检查：

```bash
docker info
nvidia-container-cli info
docker compose config
```

重新运行：

```bash
make rebuild
make gpu-check
```

不要在容器中执行：

```bash
pip install torch
```

这可能覆盖 NGC 为 ARM64 + GB10 提供的 CUDA PyTorch。

---

## 2. `no kernel image is available for execution on the device`

GB10 计算能力为 SM121。常见原因：

- 使用了不支持 SM121 的旧 PyTorch/CUDA 镜像；
- 第三方 wheel 只编译了 x86 或较旧 GPU 架构；
- 自定义节点覆盖了 torch、triton 或 CUDA 扩展。

处理：

1. 移除最近新增的第三方节点；
2. 恢复默认 `BASE_IMAGE`；
3. 执行 `make rebuild`；
4. 执行 `make gpu-check`。

---

## 3. 容器退出码 137、系统卡顿或 SSH 中断

通常表示统一内存压力过高或系统 OOM。

立即处理：

```bash
make stop
docker ps
free -h
```

修改 `.env`：

```dotenv
RESERVE_VRAM_GB=16
VRAM_HEADROOM_GB=4
ASYNC_OFFLOAD_STREAMS=1
COMFYUI_EXTRA_ARGS=--fast-disk --disable-smart-memory
```

然后：

```bash
make restart
```

工作流同时调整：

- 分辨率下降一档；
- 时长先降至 4 秒；
- Batch 固定为 1；
- 停止其他推理和训练容器；
- 不开启高分辨率预览缓存。

仅在故障诊断且理解影响时，可清理 Linux 文件缓存：

```bash
sudo sync
echo 3 | sudo tee /proc/sys/vm/drop_caches
```

这不是日常提速命令，也不能替代降低任务规模。

---

## 4. `nvidia-smi` 不显示显存总量或显存列为 N/A

DGX Spark 是统一内存架构。部分传统离散 GPU 显存指标在 GB10 上不可用或不能准确反映可供 GPU 使用的物理内存。

重点观察：

```bash
free -h
docker stats --no-stream
dmesg -T | grep -Ei 'oom|killed process'
```

不要只依据 `nvidia-smi` 的显存列判断是否有内存余量。

---

## 5. ComfyUI 中找不到模型

确认路径：

```bash
make verify-models
```

应分别位于：

```text
models/diffusion_models/
models/text_encoders/
models/vae/
```

检查 Compose 实际挂载：

```bash
docker compose config
docker inspect minimax-h3-comfyui --format '{{json .Mounts}}' | jq
```

---

## 6. ModelScope 下载失败或校验不通过

模型来自 https://modelscope.cn/models/Comfy-Org/MiniMax-H3 。先确认文件仍与固定清单一致：

```bash
make check-model-source
```

如提示认证失败，在 `.env` 填写 ModelScope API Token 后重试：

```dotenv
MODELSCOPE_API_TOKEN=your_modelscope_token
```

```bash
make download
make verify-models
```

- 下载使用国内站 API，支持同目录 `.part` 文件断点续传；服务端不支持续传时会重新下载。
- 已有模型必须通过大小和 SHA-256 校验才会跳过；校验失败可重新执行下载修复。
- 校验值固定在 `docker/model_manifest.json`；如上游文件变化，先核实来源再更新清单，不要直接绕过校验。
- 不要并发写同一模型目录；工具会使用文件锁拒绝第二个下载/校验进程。
- 检查数据盘空间，替换损坏模型时需要同时容纳原文件和下载中的新文件。
- 旧的 `HF_TOKEN`、`HF_ENDPOINT` 和 `hf-cache/` 不参与当前模型下载。

---

## 7. 画面全黑、输出损坏或没有音频

确认使用官方匹配组合：

```text
FL2VA INT8 convrot
Qwen3-VL-32B NVFP4 AWQ
Video VAE FP16
Audio VAE FP32
```

不要统一强制所有组件为 FP16/BF16。音频 VAE 应保持官方 FP32 文件。

先恢复官方 Template Library 工作流，关闭第三方节点和自定义采样参数，再做 608×352、4 秒测试。

检查输出文件：

```bash
ffprobe -hide_banner "$H3_DATA_ROOT/output/<文件名>.mp4"
```

## 8. 网页打不开

服务器检查：

```bash
make status
ss -ltnp | grep 8188
```

个人电脑重新建立 SSH 隧道：

```bash
ssh -N -L 8188:127.0.0.1:8188 nvidia@<服务器IP>
```

浏览器访问：

```text
http://127.0.0.1:8188
```

## 9. 首次启动长时间停在加载阶段

首次启动会初始化 CUDA、扫描模型目录并加载前端。查看：

```bash
make logs
```

若日志仍持续更新，不要反复重启。若出现明确 Traceback，执行：

```bash
make diagnostics
```

## 10. SageAttention 是否现在安装

基线阶段不安装。

原因：

- GB10 为 SM121；
- 通用预编译 wheel 未必包含 SM121；
- 源码编译会引入 CUDA、编译器和 torch ABI 变量；
- 一旦失败，很难区分是 H3、ComfyUI 还是注意力扩展问题。

先完成官方量化基线。随后单独复制环境或建立新镜像层测试，并保留无 SageAttention 的可回滚镜像。

---

## 11. 旧版 torchaudio ABI 问题与当前运行环境

NGC 25.11 / ComfyUI v0.30.0 的历史部署需要单独编译 torchaudio，才能匹配 NGC 的定制 torch。

当前升级至 ComfyUI v0.45.0，其 H3 节点和音频预处理均使用 `comfy.audio`，不再需要 torchaudio。不要继续沿用旧的源码编译或 `docker commit` 安装步骤。

应用在容器内 `/opt/h3-venv` 运行，使用固定的上游稳定依赖；NGC 原有的 Python 包与应用隔离。

```bash
make build
make gpu-check
make up
docker exec minimax-h3-comfyui python -c "import torch, comfy.audio; print(torch.__version__, torch.version.cuda)"
make smoke
```

如已有 `comfyui-src/` 缺少 `.h3-source-ref` 标记或与 `.env` 的 `COMFYUI_REF` 不一致，先移走旧目录，再执行 `make build`。

## 12. 生成视频默认带声音（用户偏好，2026-08-04 钉死）

**用户要求**：所有 H3 视频生成默认带原生音效，不要静音版。

**原因**：H3 是音画联合模型，但音频需要显式接解码节点才输出。
早期 workflow 只接了视频解码（VAEDecode），没接音频解码（VAEDecodeAudio），
导致噜噜/噜妹/鲸鱼等视频全部无声。

**标准 workflow 音频三件套**（必须全部接上）：

```json
"audio_vae_loader": {"class_type": "VAELoader", "inputs": {"vae_name": "minimax_h3_audio_vae_fp32.safetensors"}},
"audio_decode": {"class_type": "VAEDecodeAudio", "inputs": {"samples": ["sampler", 0], "vae": ["audio_vae_loader", 0]}},
"audio_save": {"class_type": "SaveAudio", "inputs": {"audio": ["audio_decode", 0], "filename_prefix": "audio/h3_xxx"}}
```

**音频 VAE 用官方 FP32 文件**（`minimax_h3_audio_vae_fp32.safetensors`），不要降精度。
音频输出后需用 ffmpeg 与视频 mux 合成带声 MP4。

**要点**：
- 提示词里写清音效描述（如"柴火噼啪声和夜晚虫鸣"），模型会生成对应音效
- 视频 VAE（fp16）与音频 VAE（fp32）是两个不同文件，别混用
- SaveAudio 默认存到 output/audio/ 子目录

## 13. H3 生成的视频有音轨但几乎听不到（音量极低）

**现象**：视频有音轨（ffprobe 能看到 aac/flac），但人耳几乎听不见声音。

**根因**：H3 音频 VAE 解码出的音效电平极低——实测峰值约 **-34 dB**、RMS 约 **-50 dB**
（正常听感峰值应在 -3~-6 dB）。"轻微噼啪声"类提示词会被模型理解成超轻声。
不是微信传输问题，文件本身音轨完好。

**验证方法**：

```bash
ffmpeg -i out.flac -af astats=metadata=1 -f null - 2>&1 | grep -E "Peak level dB|RMS level dB"
# 峰值 < -20 dB 即视为音量过低
```

**修复**（loudnorm 动态响度归一化，推荐）：

```bash
ffmpeg -y -i video_with_audio.mp4 \
  -af "loudnorm=I=-16:TP=-1.5:LRA=11" \
  -c:v copy -c:a aac out_loud.mp4
# 归一化后峰值约 -3.4 dB，RMS 约 -20 dB
```

**经验**：
- 生成后**一律跑 loudnorm**，不要跳过；这是 H3 音频的标准后处理步骤
- 提示词里写音效时可用 "clear and audible ..." 强调音量，但最稳的还是 loudnorm
